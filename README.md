## About

I am a Computer Science engineer who builds software that is expected to survive contact with real users, real traffic, and real adversaries. My work sits at the intersection of **product engineering**, **applied AI**, and **offensive security** — designing systems end to end, from data model and API contract to interface, deployment pipeline, and threat surface.

On the **software engineering** side, I build full stack applications with a strong bias toward correctness, maintainability, and measurable performance: typed codebases, normalized schemas, row-level authorization, CI-enforced quality gates, and instrumentation that makes regressions visible before users find them.

On the **AI/ML** side, I design and ship agentic systems — retrieval pipelines, tool-using LLM agents, structured-output contracts, evaluation harnesses, and cost/latency budgets — rather than treating models as a thin wrapper over a prompt.

On the **security** side, I operate as a practitioner: responsible disclosure, bug bounty research, CTF competition, reverse engineering, and building my own tooling for reconnaissance and assessment. I founded **RAVEN'34**, a student penetration testing division, to formalize that practice.

I approach every build with a **product engineering mindset** — scope defined by user outcome, architecture defined by constraints, and shipping defined by evidence.

## Featured Projects

<details>
<summary><b>PrepGenie — Agentic AI Career Coaching Platform</b></summary>

<br/>

An agentic AI platform that conducts adaptive interview preparation: it parses a candidate's resume and target role, generates a personalized competency map, runs multi-turn mock interviews, and returns structured, evidence-backed feedback instead of generic advice.

| | |
| :--- | :--- |
| **Stack** | FastAPI · Next.js 14 · TypeScript · Supabase (Postgres + Auth + RLS) · Gemini API · Tailwind CSS |
| **Scale** | Multi-tenant session model, persisted interview transcripts, async job handling for long-running generations |
| **Performance** | Streamed token delivery for sub-second perceived latency; cached embedding and prompt layers to cut redundant model calls |
| **Security** | Row-level security on every tenant table, server-side key custody, schema-validated model output, rate-limited generation endpoints |
| **Impact** | Built and shipped for the HACK AI hackathon; converts an unstructured job search into a measurable, iterative feedback loop |
| **Repository** | [View Repository](https://github.com/shubh4m03) |

The engineering challenge here was not calling a model — it was making a non-deterministic system behave like a product. Every agent response is constrained to a typed schema, validated at the boundary, and rejected-and-retried on contract violation. The backend treats the LLM as an unreliable dependency: budgeted, timed out, and always paired with a deterministic fallback so a degraded model never becomes a broken user experience.

</details>

<details>
<summary><b>ShiftPin — Enterprise Staff Attendance & Workforce Tracker (PWA)</b></summary>

<br/>

A production progressive web application for workforce attendance at Raj Laxmi Enterprises, built for staff who work from low-end Android devices on unreliable connectivity — installable, offline-tolerant, and resistant to proxy punch-ins.

| | |
| :--- | :--- |
| **Stack** | React · TypeScript · Supabase (Postgres + Auth + Realtime) · Service Workers · Tailwind CSS · PWA Manifest |
| **Scale** | Multi-role deployment across admin and staff tiers with realtime attendance state and auditable historical records |
| **Performance** | App-shell caching and offline queueing so punch events survive network loss and reconcile on reconnect |
| **Security** | Admin-only account provisioning, device-binding to prevent shared-credential fraud, RLS-enforced record isolation, immutable audit trail |
| **Impact** | Replaced manual register-based attendance with a verifiable digital system for a live commercial operation |
| **Repository** | [View Repository](https://github.com/shubh4m03) |

The hard requirement was integrity, not features. Attendance systems fail when one employee can punch in for another, so the architecture binds a staff account to a registered device fingerprint and enforces provisioning exclusively through the admin tier. Offline-first behavior was mandatory rather than aspirational: events are queued locally and reconciled server-side with conflict rules, so connectivity never becomes an excuse for a missing record.

</details>

<details>
<summary><b>RAVEN-Recon — Terminal-Native Reconnaissance Aggregator</b></summary>

<br/>

A TUI-first reconnaissance orchestration framework that drives an industry-standard tool chain end to end and normalizes every result into one queryable dataset — designed to run entirely inside the terminal, with no browser, no external window, and no dependency on a GUI.

| | |
| :--- | :--- |
| **Stack** | Python · Textual (TUI) · asyncio · subfinder · httpx · naabu · nuclei · SQLite |
| **Scale** | Concurrent subdomain enumeration, probing, port scanning, and template-based scanning across large target scopes |
| **Performance** | Async task orchestration with bounded worker pools, rate control, incremental result streaming to the interface |
| **Security** | Scope enforcement guardrails, engagement-bound target validation, local-only result storage, no third-party telemetry |
| **Impact** | Collapses a fragmented manual recon workflow into a single reproducible pipeline for pentest and red team engagements |
| **Repository** | [View Repository](https://github.com/shubh4m03) |

Recon is usually a pile of shell history and inconsistent output formats. This tool treats it as a data pipeline: each stage emits normalized records into a local store, later stages consume upstream output automatically, and the interface renders live progress without blocking the pipeline. The scope guardrail is a first-class component — targets outside the declared engagement boundary are rejected before any packet leaves the host.

</details>

<details>
<summary><b>SG-Portfolio — High-Performance Static Engineering Portfolio</b></summary>

<br/>

A zero-runtime-JavaScript engineering portfolio built on a content-driven static architecture, optimized for near-perfect Lighthouse scores and instant first paint on constrained networks.

| | |
| :--- | :--- |
| **Stack** | Astro · TypeScript · Tailwind CSS · GitHub Actions · GitHub Pages |
| **Scale** | Fully static output, content-collection driven, deployed on CDN-backed hosting |
| **Performance** | Island-based hydration with default zero client JS, pre-rendered routes, optimized asset pipeline |
| **Security** | No server surface, no third-party trackers, strict CI-controlled deployment path |
| **Impact** | A portfolio that demonstrates performance engineering by being the artifact, not by describing it |
| **Repository** | [View Repository](https://github.com/shubh4m03/SG-Portfolio) |

Every dependency here had to justify its bytes. Content lives in typed collections so the build fails on malformed data rather than shipping a broken page, and the entire deploy path runs through GitHub Actions with no manual publish step — the same discipline applied to a personal site that I would apply to a production service.

</details>

<details>
<summary><b>Kitchenette — Campus Food Ordering SPA</b></summary>

<br/>

A three-role campus food ordering single-page application implementing the complete order lifecycle — customer, vendor, and administrator — with client-persisted state and a fully deterministic state machine.

| | |
| :--- | :--- |
| **Stack** | JavaScript · HTML5 · CSS3 · LocalStorage persistence · Component-based SPA architecture |
| **Scale** | Three distinct role surfaces sharing a single normalized client-side data layer |
| **Performance** | Instant route transitions with no network round trips; O(1) state reads from an indexed store |
| **Security** | Role-scoped view gating, validated state transitions, defensive handling of corrupted persisted state |
| **Impact** | Delivered a complete multi-role commerce workflow without any backend dependency |
| **Repository** | [View Repository](https://github.com/shubh4m03) |

The constraint — no backend — forced the interesting design work into the data layer. Orders move through an explicit state machine where invalid transitions are rejected rather than silently applied, and the persistence layer is versioned so a schema change does not brick a returning user's stored state.

</details>
